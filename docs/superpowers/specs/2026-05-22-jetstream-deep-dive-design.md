# JetStream Deep Dive — Design Spec

**Date:** 2026-05-22
**Status:** Draft for implementation
**Audience for this spec:** the writer (Claude or human) of the first pass

---

## 1. Goal

Land the first **deep dive** in the NATS documentation site: an end-to-end,
Rust-book-style chapter on JetStream (streams + consumers). It is the
pilot for a new "Learn" docs section that will, over time, hold sibling
deep dives for KV, Object Store, Clustering & Operations, and Security.

The chapter is the *long-form learning* layer. It sits between the
short **Core Concepts** primers and the exhaustive, versioned **Reference**.

### 1.1 Problems we are fixing

The legacy `nats.docs` JetStream content (used here as a *source of
truth for facts*, not for structure) has four recurring problems we
must not reproduce:

1. **Inconsistent wording** — same thing called different names across
   pages.
2. **Stream-of-consciousness paragraphs** — multiple ideas per
   paragraph, no clear teaching beat.
3. **Premature depth** — full retention/ack/replication matrices in the
   first encounter, before the reader has the vocabulary.
4. **Inline reference data** — every option's full description embedded
   in prose, leaving no clean handoff to the actual reference.

### 1.2 Non-goals

- Not teaching KV, Object Store, or any non-stream JetStream feature.
- Not teaching cluster operations beyond "what replication buys you"
  (one page).
- Not version-conditional content. The deep dive is *unversioned*
  (timeless concepts only). All version-bound behavior is linked out to
  versioned Reference.
- Not a tutorial in the Docusaurus "tutorials" sense — those are
  task-shaped. This is a learning path.

---

## 2. Decisions (resolved during brainstorming)

| Topic | Decision |
|---|---|
| Placement | New top-level `Learn` docs plugin instance, own sidebar |
| Scope of first deep dive | Core JetStream only: streams, consumers, ack, retention, replication primer. Excludes KV, Object Store, ops/clustering depth |
| Reader assumption | Reader has read Core Concepts (pub-sub, subjects, request-reply, queue-groups). No re-teaching of those |
| Versioning | Unversioned. Concepts only. Version-specific behavior delegated to versioned Reference |
| Progression style | A — single running scenario (an `ORDERS` stream) that grows across all pages |

## 3. Files & sidebar plumbing

### 3.1 New docs plugin instance

Mirror the existing `reference` plugin pattern. `docusaurus.config.ts`
gets a third `@docusaurus/plugin-content-docs` instance:

```ts
[
  '@docusaurus/plugin-content-docs',
  {
    id: 'learn',
    path: 'learn',
    routeBasePath: 'learn',
    sidebarPath: './sidebars-learn.ts',
    includeCurrentVersion: true,
    // no versioning yet — single current version
  },
]
```

A new `sidebars-learn.ts` modeled on `sidebars-reference.ts` exports a
single `learnSidebar`. It is **authored by hand** (unlike the reference
sidebars, which are generated by `scripts/generate-version.js`).

Navbar (`docusaurus.config.ts`): add a `Learn` item between `Docs` and
`Reference`, pointing to `/learn`.

### 3.3 Cross-link from Core Concepts

`docs/concepts/jetstream.md` stays as the short conceptual primer but
gains, near the top (just under the opening 2 paragraphs), an
admonition:

```mdx
:::tip Want the full chapter?
This page is the short version. For a step-by-step, runnable walkthrough
that builds an `ORDERS` stream from scratch, see the
[JetStream deep dive](/learn/jetstream).
:::
```

No content is *moved* from `concepts/jetstream.md` — it remains a valid
"five-minute overview." Duplication of the high-level "what is a stream"
sentence between concepts and Learn is acceptable and intentional.

### 3.4 URL stability

URLs of the form `/learn/jetstream/<page>` are part of the spec.
Renaming pages later is a breaking link change and should be avoided
once shipped.

## 4. Page-by-page outline

Throughout, **scenario state** carried forward is noted. The reader
should be able to keep their CLI session open across pages without
resetting.

### 4.1 Master scenario

A single fictional service — **order events**. Subjects:

- `orders.created`
- `orders.shipped`
- `orders.cancelled`

One canonical message shape (used identically across CLI/JS/Go/etc.):

```json
{
  "order_id": "ord_8w2k",
  "customer": "acme-co",
  "total_cents": 4200,
  "ts": "2026-05-22T10:14:22Z"
}
```

This shape is pinned in this spec — every language example in the
chapter publishes/consumes this exact shape.

### 4.2 Page table

Numbering: page 0 is the chapter intro (`learn/jetstream/index.md`).
Pages 1–11 are the content pages, ordered by sidebar position.

| # | Slug | Teaches | Reader leaves with | Defers to reference |
|---|---|---|---|---|
| 0 | `index` | What this chapter is, who it's for, how it reads | A mental map: stream + consumer + ack = the whole game | — |
| 1 | `why-a-stream` | Why core NATS isn't enough for orders: late subscribers, restarts, redelivery. The stream as a "log you can replay" | When a stream is the right answer (and when pub-sub still is) | — |
| 2 | `your-first-stream` | `nats stream add ORDERS` with `--subjects=orders.>` and defaults. Inspect with `nats stream info`. STATE: empty ORDERS stream exists | Anatomy of a stream config printout; subjects → stream binding | All non-default config flags → Reference: Stream Configuration |
| 3 | `publishing` | Sync publish; `PubAck` (sequence, stream, duplicate flag). One-line each on async + dedup header. STATE: 3 orders stored | The PubAck contract; "stored ≠ delivered" mental model | Headers, batch publish, expected-state → Reference: Headers |
| 4 | `reading-back` | Ephemeral consumer to *replay* what's stored. No acks yet. STATE: 3 orders visible from start of stream | Streams ≠ topics — you can re-read whenever you want | — |
| 5 | `your-first-consumer` | `nats consumer add ORDERS shipping --ack=explicit --pull`. Pull + explicit ack + redelivery on no-ack. STATE: `shipping` consumer in play | What a "durable consumer" really tracks (the seq cursor); ack/redeliver loop | Push consumers, Nak/Term/InProgress → Reference: Consumer API |
| 6 | `filtering` | Add an `analytics` consumer with `--filter=orders.shipped`. Two consumers reading the same stream at different positions. STATE: two consumers | Consumers as independent views; filter as the cheap fan-out tool | Multi-filter, subject transform → Reference: Consumer Configuration |
| 7 | `worker-pool` | Three workers sharing the `shipping` consumer (pull from same name). `MaxAckPending`, in-flight redelivery on worker crash. STATE: 3 workers | Consumer-level work distribution (vs. core NATS queue groups) | AckWait tuning, backoff arrays → Reference: Consumer Configuration |
| 8 | `shaping-the-stream` | Storage policies: `MaxAge`, `MaxBytes`, `MaxMsgs`, `Discard=Old\|New`. Updates ORDERS to 7-day retention. STATE: capped stream | What "the stream as a log" means under pressure — limits decide who wins | Per-subject limits, `MaxMsgsPerSubject` → Reference: Stream Configuration |
| 9 | `delivery-semantics` | The three retention policies: Limits / Interest / WorkQueue. Picks one per archetype (audit log / fan-out / queue) | Which retention to reach for; the trap of switching after-the-fact | Stream republish, mirror/source → Reference: Stream Configuration |
| 10 | `surviving-node-loss` | `R=3`, leader concept, what "the stream has a leader" actually means for writes/reads. If a local single-node demo can't show it, link to a future cluster guide and explain conceptually | When `R=1` is dangerous; `R=3` as the prod floor | Placement, tags, mirror DR, account limits → future Ops deep dive |
| 11 | `where-next` | Pointers to: KV deep dive (when written), Object Store deep dive (when written), Ops & Clustering deep dive (when written), Reference root | A map of what's beyond this chapter | — |

### 4.3 Length targets

- Each page: **150–300 lines of source** (frontmatter + prose + code +
  components).
- Hard cap: 400 lines. Above that, split.
- Stream-of-consciousness check on review: if a paragraph carries two
  unrelated ideas, split it.

## 5. Voice & wording rules

### 5.1 Voice

- **One thought per paragraph.** Every paragraph has a single teaching
  beat. If you can summarize it as two sentences with "and", split it.
- **Define-then-use.** Never use a term before its dedicated paragraph
  in this or a prior page.
- **Step-by-step depth.** Each page introduces **≤2 new concepts**. If a
  third sneaks in, kick it to a later page or to Reference.
- **Active voice, present tense** (matches existing concept pages).
- **No filler.** "It is important to note that…", "Basically…",
  "Essentially…" — all out.

### 5.2 Wording lockfile

Same word for same thing across the chapter. Authoritative list:

| Term | Use | Don't use |
|---|---|---|
| stream | "stream" | "JetStream stream", "topic", "channel" |
| consumer | "consumer" | "subscription", "subscriber" (those are core NATS) |
| message | "message" | "event", "record" (except in scenario prose where domain matters) |
| ack | "ack" (after first introduction as "acknowledgment") | "ack-ed", "acknowledged" in body |
| pull consumer / push consumer | always two lowercase words | "Pull-Consumer", "PullConsumer" |
| Reference | when referring to the reference docs section | "the docs", "the spec", "the manual" |
| publish | "publish" | "send" (reserve "send" for core NATS) |
| store | "stored in the stream" | "saved", "persisted" (one-time intro of "persistence" OK) |

A `learn/jetstream/glossary.md` file is **not** created in the first
pass — the lockfile lives only here in the spec.

### 5.3 Reference handoff phrase

Greppable, used verbatim where applicable:

> The full set of `<X>` options is documented in
> [Reference → `<Path>`](/reference/...). We use only `<Y>` here.

Each Learn page ends with a "**See also**" section: **1–3** reference
links, hard maximum.

## 6. Example pattern

Matches the project's existing `CLAUDE.md` rules.

### 6.1 Default: `nats-example` tags

For every non-trivial snippet, use:

```mdx
<div class="nats-example"
     data-type="learn-jetstream-<page-slug>-<snippet>"
     data-languages="cli,js,go,python,java,rust,csharp"></div>
```

Example IDs follow `learn-jetstream-<page>-<snippet>`, e.g.:

- `learn-jetstream-your-first-stream-create`
- `learn-jetstream-publishing-pubAck`
- `learn-jetstream-your-first-consumer-pullAndAck`

This will trigger work in the client-example repos (out of scope for
this spec but tracked in the implementation plan).

### 6.2 When inline Tabs are OK

Only when:

- **CLI-only** (server startup, `nats stream info`, etc.) — use a plain
  fenced bash block, not a Tabs block.
- **Language-only API** that has no analog in other clients (rare in
  this chapter).

### 6.3 Data shape is pinned

The ORDERS JSON shape from §4.1 is the same across every language. No
language gets to invent its own payload. This is enforced by the
example IDs (one ID per logical snippet, fetched into multiple
languages).

### 6.4 Languages in `data-languages`

Always the full set: `cli,js,go,python,java,rust,csharp`. If a given
client repo hasn't shipped the example yet, the fetch will skip it
gracefully — no need to omit the language from the tag.

## 7. Reference handoff — what stays vs. what goes

| Belongs in Learn | Belongs in Reference |
|---|---|
| The *why* and *when* of a feature | Full type/range/default of every config option |
| One runnable happy path | Exhaustive option/flag tables |
| One annotated CLI output | Every error code, every advisory schema |
| The failure mode that teaches the concept (one of, not all) | Every wire-protocol header |
| A pinned ORDERS scenario | Version-specific behavior |

**Tactical rule of thumb:** if removing the detail would not change the
reader's mental model of how the feature works, it does not belong in
Learn.

## 9. Scope of the first implementation pass

The implementation plan (the next artifact, written via `writing-plans`)
will decide *which subset* of the 11 pages lands in the first PR. The
recommendation for that plan:

**First PR:**

1. Plumbing — new `learn` plugin instance, sidebar file, navbar entry,
   `learn/index.md` (Learn hub), `learn/jetstream/index.md` (chapter
   intro, page 0), `_category_.json`.
2. Three content pages fully written: page 1 (`why-a-stream`), page 2
   (`your-first-stream`), page 3 (`publishing`). The smallest set that
   proves the chapter shape and the example pattern end-to-end —
   covers a concept-only page, a CLI-driven config page, and a
   client-code page.
3. Cross-link admonition added to `docs/concepts/jetstream.md`.
4. Implementation plan tracks the remaining 8 content pages (4–11) as
   follow-up tasks, not in the first PR.

This split is a recommendation only — the implementation plan owns the
final scoping decision.

## 10. Out of scope (explicit)

- KV deep dive.
- Object Store deep dive.
- Ops & Clustering deep dive.
- Versioned Learn content. If we ever need version-specific Learn
  prose, we revisit the plugin config — but not in this pass.
- Translation. Learn ships English-only first.
- Search optimization beyond what Docusaurus gives by default.
- Auto-generation from any source. Every Learn page is hand-written
  prose; only the embedded code examples come from the `nats-example`
  pipeline.

## 11. Acceptance criteria

For the chapter as a whole (across however many PRs it takes):

- [ ] `Learn` appears in navbar.
- [ ] `/learn/jetstream` lands on the chapter intro (page 0).
- [ ] All 12 page URLs (intro + 11 content pages) return 200 and render.
- [ ] Sidebar shows the 12 pages in order, JetStream chapter open.
- [ ] Every example ID referenced in Learn exists in the client-example
      pipeline for at least CLI + JS + Go (other languages may follow).
- [ ] `npm run build` passes; no broken internal links.
- [ ] `docs/concepts/jetstream.md` carries the cross-link admonition.
- [ ] Wording lockfile (§5.2) holds — grep for forbidden terms returns
      no hits in `learn/jetstream/**`.

For each individual Learn page:

- [ ] ≤2 new concepts introduced.
- [ ] One "See also" block, ≤3 reference links.
- [ ] Scenario state matches the page table in §4.2.
- [ ] Length within 150–400 lines.
- [ ] CLI tab is default in every Tabs block; `groupId="lang"` set.
